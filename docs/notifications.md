# Notifications — Integration with cmux

Adapts ideas from [cmux notifications](https://cmux.com/docs/notifications) to Workbench’s browser + Go server architecture.

## cmux reference

| cmux concept | Workbench equivalent |
|--------------|----------------------|
| [Lifecycle](https://cmux.com/docs/notifications#lifecycle) (panel, badge, read, desktop) | `frontend/src/modules/notifications/`, poll + `useNotificationDesktopAlerts` |
| [Notification panel](https://cmux.com/docs/notifications#notification-panel) `⌘⇧I` | `NotificationPanel.vue`, same shortcut |
| Click notification → jump to workspace | `worktreeId` → `/w/:worktreeId`; with `terminalId` → `/w/:worktreeId/t/:terminalId` |
| [Custom command](https://cmux.com/docs/notifications#custom-command) env (`CMUX_NOTIFICATION_*`) | Not implemented yet (future: run user shell on notify) |
| [Claude Code hooks](https://cmux.com/docs/notifications#claude-code-hooks) | Settings → Agents → notify hooks → `~/.claude/settings.json` |
| `cmux notify --title … --body …` | `workbench-cli notify --title … --body …` |
| cmux infers `workspaceId` / `surfaceId` inside the desktop app | Workbench stamps PTY env (below) and passes IDs to the API |
| [Copilot / agent hooks](https://cmux.com/docs/notifications#copilot-cli-hooks) pattern | Same `type: command` hook shape; generated by `BuildNotifyCommand` |
| [Notification hooks](https://cmux.com/docs/notifications#notification-hooks) (JSON stdin, policy) | Not implemented; Workbench uses agent lifecycle hooks + OSC path instead |

## Targeting: how the browser knows which tab

cmux runs agents inside managed surfaces; `cmux notify` can associate the alert with the active workspace/pane (see hook JSON `workspaceId` / `surfaceId` in cmux’s [notification hooks](https://cmux.com/docs/notifications#notification-hooks)).

Workbench is HTTP-based and multi-tab in the browser, so we **inject session env at PTY spawn** and read it when hooks run:

| Variable | Role |
|----------|------|
| `WORKBENCH_TERMINAL_ID` | Terminal tab UUID (`terminals.id`) |
| `WORKBENCH_WORKTREE_ID` | Worktree UUID (`worktrees.id`) |
| `WORKBENCH_PORT` | Local server port for `workbench-cli notify` |
| `WORKBENCH` | Marker that the shell is a Workbench session |

Set in `server-go/internal/terminal/workbench_env.go` → `ApplyWorkbenchEnv` from `pty_registry.spawnPTY`.

Generated Claude hooks (via **Apply** in Agents settings) look like:

```bash
workbench-cli notify \
  --worktree-id "$WORKBENCH_WORKTREE_ID" \
  --terminal-id "$WORKBENCH_TERMINAL_ID" \
  --title "Claude Code" \
  --body "Session finished"
```

`workbench-cli notify` also reads those env vars if flags are omitted (`server-go/internal/cli/notify.go`), then `POST /api/notifications/hook` (loopback only).

**Requirement:** run the agent from a **Workbench terminal tab** so the hook inherits `WORKBENCH_*`. External terminals have no stamp; notifications are global to that server instance.

## Two notification sources

1. **Agent hooks** — Claude/Cursor `Stop`, `Notification`, etc. → shell command → `workbench-cli notify`.
2. **OSC 133 command complete** — shell integration in the PTY → `MaybeNotifyAgentComplete` with known `terminalID` + worktree (`server-go/internal/notifications/agent_notify.go`).

Both persist `worktree_id` and `terminal_id` on the `notifications` row.

## Divergences from cmux

- **Transport:** cmux CLI ↔ local socket/app; Workbench uses `http://127.0.0.1:<port>/api/notifications/hook`.
- **Targeting:** cmux can resolve workspace inside the app; we rely on PTY env + optional explicit CLI flags.
- **cmux-notify.sh:** cmux checks `[ -S /tmp/cmux.sock ]`; Workbench checks `WORKBENCH=1` implicitly via env on notify.
- **Read semantics:** opening a worktree currently marks all its notifications read (`WorkspaceView.vue`) — may change to per-terminal read when focusing a tab.
